# Upgrading to v2.10.0

The fixed super-admin bootstrap is replaced by a trusted, parameterized maintenance job that reconciles any account to an exact authentication role.

## Do I need to act?

**Required** if you deploy `jobs/init`, configure `SUPER_ADMIN_EMAIL` or `SUPER_ADMIN_PASSWORD`, or rely on `standalone-rest` to create a super-admin during startup. Replace that bootstrap before removing its job and password secret.

## Replace the init job

The `service-authentication/jobs/init` image is removed. Deploy `service-authentication/jobs/maintenance` from the same release instead. Keep the existing database settings, and add the platform URL and SMTP settings used by the REST service so the job can deliver registration links.

The stored maintenance job should have no operation arguments. Its image defaults to `--help`, so deploying it alone does not mutate authentication state. Supply an operation only for a deliberate execution:

```sh
gcloud run jobs execute AUTHENTICATION_MAINTENANCE_JOB \
  --args='account-role,--email=owner@example.com,--role=auth:superadmin,--lang=en' \
  --wait
```

Use one of `auth:anon`, `auth:user`, `auth:admin`, or `auth:superadmin`. For an existing account, the command sets that exact role and keeps the existing password. For a missing account, it sends a registration link; the user chooses their password and receives the requested role when registration completes. Repeating the same request is safe.

## Remove bootstrap credentials

Remove `SUPER_ADMIN_EMAIL` and `SUPER_ADMIN_PASSWORD` from the job and `standalone-rest` configuration. The service no longer reads them, and `standalone-rest` now runs migrations followed by REST without creating an account.

Do not remove the old init job or its password secret until the maintenance image is deployed and the required account either has the expected role or has completed its registration link. After verification, delete the legacy job and secret.

No database migration or user password reset is required.
