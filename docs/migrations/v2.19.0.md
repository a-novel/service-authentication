# Upgrading to v2.19.0

Each registration, email-change and password-reset email waits in an outbox table until the relay
accepts it. A slow relay, a network warm-up or a restart no longer loses it.

## Do I need to act?

**Recommended** for a deployment that sets `SMTP_TIMEOUT`. The service no longer reads it: a send
now times each SMTP command as RFC 5321 asks, and the health check pings the relay within 10
seconds. Delete the variable once this release runs.

**A job with a hard deadline does.** The `jobs/maintenance` image sends its invitation itself and
waits for it. A relay that stops answering ends the send within one command's timeout, at most 10
minutes, so give the job's task a deadline above that.

## Expect retries instead of 503

The routes that email a short code no longer answer 503 when the server is busy sending. They
answer 503 only during a planned downtime, as every route does.

A temporary failure retries after 30 minutes, after 60 more, then every 2 hours, until the first
code expires. Each retry sends a fresh code and invalidates the previous one. A permanent refusal, or
a send whose result is unknown, ends the email and reaches Sentry, and its user asks for another.
