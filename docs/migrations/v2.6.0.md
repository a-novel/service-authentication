# Upgrading to v2.6.0

`GET /v2/healthcheck` returns HTTP 503 when PostgreSQL, SMTP, or JSON Keys is unhealthy.

## Do I need to act?

**Required** if your health-check caller expects every response to succeed. Handle HTTP 503 as not ready. The JavaScript client's `health()` promise rejects on this response.

## Handle readiness failures

Previously, callers received HTTP 200 and inspected dependency statuses. HTTP 200 now means all dependency probes succeeded; HTTP 503 means at least one failed. Transport failures also mean readiness could not be established.

The JSON report keeps its existing dependency names and sanitized `up`/`down` statuses, including on HTTP 503. Read it for diagnostics after checking the response status. Use `GET /v2/ping` for process-only liveness.

## Roll out and verify

Deploy the service before simplifying consumers to rely only on HTTP success. Keep dependency-status checks while older instances can still serve requests; publishing a client package does not update those instances.

In a test environment, verify HTTP 200 with healthy dependencies and HTTP 503 when a dependency is unavailable. Confirm that the response still reports every dependency and that `/v2/ping` remains successful while the process is running.

No secret rotation or database migration is required by this health-check change.
