# Upgrading to v2.24.0

An email change now asks for the account's current password, as a password change does, and tells the former address once it applies. A password or email change ends every session opened before it, but the caller's. The waitlist answers every accepted request alike.

## Do I need to act?

**Required** for a client that changes account emails, the account platform today. Ship the client changes below before this release reaches production: a v2.23 server ignores the new fields, so the client can send them first.

## Send the current password with an email change

`PUT /v2/short-code/update-email` requires `currentPassword`. A missing one answers 422, a wrong one 403.

```diff
 shortCodeCreateEmailUpdate(api, accessToken, {
+  currentPassword,
   email,
   lang,
 });
```

## Name the notice language when confirming an email change

`PATCH /v2/credentials/email` requires `lang`, the language of the notice the former address receives. A missing one answers 422. A server that cannot take the notice answers 503 and changes nothing.

```diff
 credentialsUpdateEmail(api, accessToken, {
   userID,
   shortCode,
+  lang,
 });
```

## Keep the caller's tokens from a password or email change

Once a password or email changes, every session opened before it ends:

- `PATCH /v2/session` answers 403 to its refresh tokens, and the token endpoint answers `invalid_grant`.
- `GET /v2/session` and `POST /v2/oauth/authorization-code` answer 401 to its access tokens. Services that verify access tokens offline accept them until they expire.

The caller's session continues. `PATCH /v2/credentials/password` and `PATCH /v2/credentials/email` answer the account with a `token` member: a fresh pair that joins the caller's session and ends with it. Replace the session's tokens with it.

```diff
-await credentialsUpdatePassword(api, accessToken, form);
+const { token } = await credentialsUpdatePassword(api, accessToken, form);
+if (token) storeSession(token);
```

`token` is absent when no session of the account made the request: an email confirmation sent with an anonymous token, or a password reset, which then signs the person in with the new password.

## Expect 202 from the waitlist

`PUT /v2/waitlist` no longer answers 409 `account_exists` or `already_waitlisted`. A listed or registered address answers 202, like a new one, and changes nothing. `WaitlistJoinConflictError` stays exported and deprecated, so a client built against v2.24.0 still reads the 409 of a v2.23 server during the rollout.
