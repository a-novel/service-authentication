# Upgrading to v2.24.0

An email change now asks for the account's current password, as a password change does, and tells the former address once it applies. A password or email change ends every session opened before it. The waitlist answers every accepted request alike.

## Do I need to act?

**Required** for a client that changes account emails, the account platform today. Ship the client changes below before this release reaches production: a v2.23 server ignores the new fields, so the client can send them first.

## Send the current password with an email change

`PUT /v2/short-code/update-email` requires `currentPassword`. A missing one answers 422, a wrong one 403.

```diff
 shortCodeCreateEmailUpdate(api, accessToken, {
+  currentPassword,
   email,
   lang,
 });
```

## Name the notice language when confirming an email change

`PATCH /v2/credentials/email` requires `lang`, the language of the notice the former address receives. A missing one answers 422. A server that cannot take the notice answers 503 and changes nothing.

```diff
 credentialsUpdateEmail(api, accessToken, {
   userID,
   shortCode,
+  lang,
 });
```

## Sign in again after a password or email change

Once a password or email changes, refresh tokens issued before it no longer renew: `PATCH /v2/session` answers 403, and the token endpoint answers `invalid_grant`. `POST /v2/oauth/authorization-code` answers 401 to an access token issued before the change. Access tokens last until they expire. The person who made the change signs in again, which a client can do at once after a password change, since it holds the new password.

## Expect 202 from the waitlist

`PUT /v2/waitlist` no longer answers 409 `account_exists` or `already_waitlisted`. A listed or registered address answers 202, like a new one, and changes nothing. `WaitlistJoinConflictError` stays exported and deprecated, so a client built against v2.24.0 still reads the 409 of a v2.23 server during the rollout.
